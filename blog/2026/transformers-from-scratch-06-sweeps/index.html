Transformers: from scratch to production · lesson 6 of 10 · all lessons · run on Kaggle · open in Colab · code on GitHub

Meta trained Llama 3 405B on up to sixteen thousand H100 GPUs; its model card counts 30.84 million GPU hours. Nobody tunes a run like that by trying things out.

The paper’s learning rate, \(8 \times 10^{-5}\) with 8,000 steps of warm-up, and the size of the model itself were chosen on much smaller models and extrapolated [1]. OpenAI said the same of GPT-4: “for very large training runs like GPT-4, it is not feasible to do extensive model-specific tuning” [2].

Each GPT-3 model got a learning rate of its own, larger the smaller the model, and ours sits roughly on the extension of that line. It got there by accident: its learning rate came from a formula in the 2017 paper, written for a model several times its size, and nobody has checked it since lesson 3.

That matters more than it sounds. In 2018 Melis et al. retuned the language models of the day with thousands of automatic trials and found that “LSTMs outperform the more recent models, contra the published claims”: a good part of the published progress had been tuning[3].

Lesson 5 compared architectures at one learning rate. This lesson asks what the settings themselves are worth, and spends an hour of a free GPU finding out.

What you’ll do

  1. Track every training run with Weights & Biases, with or without an account.
  2. Find the range of learning rates that work, for the 2017 design and for lesson 5’s, in a minute each.
  3. Write random search and successive halving from scratch and spend a fixed GPU budget on them.
  4. Train the winner to the end and check it against lesson 5’s model, with the bootstrap and with lesson 5’s seed runs.
  5. Run the same kind of search as a W&B Sweep, with Bayesian optimization and early stopping, and publish the tuned model.

What you need: a GPU. On Kaggle, Settings → Accelerator → GPU; on Colab, Runtime → Change runtime type → T4 GPU.

A free Weights & Biases account is optional: add your API key as the secret WANDB_API_KEY (Kaggle: Add-ons → Secrets; Colab: the key icon on the left) to see the runs online and run the sweep of section 8.

Without it everything else runs the same, and the runs are kept on disk. The notebook runs in about an hour and ten minutes.

1. What we tune, and what we can spend

Five knobs: the peak learning rate and the warm-up of the schedule, dropout, label smoothing, and the size of a batch in tokens. Lesson 3 took all five from the 2017 paper.

The budget: Kaggle gives a free account about 30 hours of GPU a week, and Colab promises nothing at all. An epoch of our model takes about a minute on a T4 (lesson 5), so an hour buys some sixty epochs, three trainings of the length of lesson 3’s. Tuning on a budget is mostly deciding what not to train.

The data, the tokenizer and the batches, as in lesson 5. Since the batch size is one of the things we tune, the training pairs are cut into batches of three sizes, once:

2. Tracking runs with Weights & Biases

Lessons 3 to 5 kept their results in print statements: a validation loss per epoch, scrolled past and gone. With two dozen runs ahead that stops working.

Weights & Biases (W&B) is an experiment tracker: every run records its configuration, everything you log, the load on the machine and the version of the code, and shows the runs side by side.

Four calls are all it takes: wandb.init starts a run with its configuration, run.log adds a row of numbers, run.summary keeps the final ones, run.finish closes the run. Without a key the same calls write to disk (mode="offline"), and wandb sync uploads them later. One epoch of lesson 5’s recipe, measured after each half:

run = wandb.init(project=PROJECT, mode=WANDB_MODE,
                 name="lesson 6: lesson 5's recipe, one epoch",
                 config={"peak_lr": 1e-3, "warmup": 1_000, "dropout": 0.1,
                         "label_smoothing": 0.1, "batch_tokens": 6_000})
config = run.config  # the hyperparameters, stored with the run

random.seed(SEED)
model = new_model(dropout=config.dropout)
optimizer = training.adam(model)


def schedule(step):
    return config.peak_lr * min(step / config.warmup, math.sqrt(config.warmup / step))


half_epoch = len(batches[config.batch_tokens]) // 2
steps = 0
for half in range(1, 3):  # two halves of an epoch, measured after each
    losses = training.train_steps(model, optimizer, batches[config.batch_tokens], schedule,
                                  half_epoch, pad_id=PAD, first_step=steps + 1,
                                  label_smoothing=config.label_smoothing, device=device)
    steps += len(losses)
    loss = training.validation_loss(model, valid_batches, pad_id=PAD, device=device)
    run.log({"epochs": half / 2, "train loss": np.mean(losses), "validation loss": loss})

3. The learning rate first

Of all the settings, the learning rate matters most, and it comes with the most quoted sentence of the field’s folklore[4]:

This is often the single most important hyper-parameter and one should always make sure that it has been tuned (up to approximately a factor of 2).

Yoshua Bengio

Before searching for it, find out where to search.

A learning-rate range test finds the range in one short run. Smith (2017) raised the learning rate linearly and watched the accuracy; the version most people use, from the fastai library, multiplies it by the same factor at every step, so that it sweeps several orders of magnitude, and watches the loss.

While the rate is too small, nothing happens; in the useful range the loss falls fast; beyond it, training breaks down.

def range_test(setup, start=1e-6, end=1.0, n_steps=600):
    random.seed(SEED)
    model = new_model(setup)
    optimizer = training.adam(model)
    factor = (end / start) ** (1 / n_steps)  # the same multiplication at every step

    def sweep_rate(step):
        return start * factor ** (step - 1)

    losses = training.train_steps(model, optimizer, batches[6_000], sweep_rate, n_steps,
                                  pad_id=PAD, device=device)
    rates = [sweep_rate(step) for step in range(1, len(losses) + 1)]
    return rates, losses


RANGE_STEPS = 600 if not SMOKE else 20
ranges = {}
for name, setup in [("2017 design", DESIGN_2017), ("lesson 5's design", LLAMA_STYLE)]:
    ranges[name] = range_test(setup, n_steps=RANGE_STEPS)

def until_diverged(rates, losses):
    """The test ends where the loss stops being a number, and so does the curve."""
    losses = np.asarray(losses, dtype=float)
    broken = np.flatnonzero(~np.isfinite(losses))
    end = broken[0] if len(broken) else len(losses)
    smooth = pd.Series(losses[:end]).rolling(15, min_periods=1).mean().to_numpy()
    return np.asarray(rates[:end]), smooth


fig, ax = plt.subplots(figsize=(6.4, 3.4))
for (name, (rates, losses)), color in zip(ranges.items(), [COLORS["muted"], COLORS["att"]]):
    rates, smooth = until_diverged(rates, losses)
    ax.plot(rates, smooth, color=color, label=name)
ax.set_xscale("log")
ax.set_ylim(top=12)
ax.set_xlabel("learning rate (rising every step)")
ax.set_ylabel("training loss, smoothed")
ax.set_title("A learning-rate range test")
ax.legend()
plt.show()

for name, (rates, losses) in ranges.items():
    rates, smooth = until_diverged(rates, losses)
    best_rate = rates[int(np.argmin(smooth))]
    print(f"{name}: lowest loss at a learning rate of {best_rate:.1e}")

Both models learn fastest around the same learning rate, a few times \(10^{-3}\), well above lesson 3’s peak. The difference is where they break.

Key point

The 2017 design falls apart at a learning rate many times lower than lesson 5’s design does. That is pre-norm’s gift, which lesson 5’s ablation couldn’t see: not a better model, a wider range of learning rates that work, which makes a model easier to tune and harder to break. At Llama’s scale, where a diverged run costs millions, that is the point.

4. Random search

Five knobs, each with a range. The obvious search is a grid: three values of each, every combination, \(3^5 = 243\) runs, four days of our GPU.

Random search draws every setting at random instead, and Bergstra and Bengio (2012) showed it is the better use of the same number of trials. Usually only a few knobs matter, and a grid spends its trials repeating the same few values of exactly those:

The ranges. The learning rate and the warm-up are drawn on a logarithmic scale, since going from \(10^{-4}\) to \(2 \cdot 10^{-4}\) is as big a step as from \(10^{-3}\) to \(2 \cdot 10^{-3}\); dropout and label smoothing on a linear one; the batch from three sizes. Eighteen configurations, the first six of them:

search_rng = random.Random(SEED)


def log_uniform(low, high):
    return 10 ** search_rng.uniform(math.log10(low), math.log10(high))


def sample_config():
    return {
        "peak_lr": log_uniform(2e-4, 1e-2),
        "warmup": int(log_uniform(200, 4_000)),
        "dropout": search_rng.uniform(0.0, 0.3),
        "label_smoothing": search_rng.uniform(0.0, 0.2),
        "batch_tokens": search_rng.choice(BATCH_TOKENS),
    }

5. Successive halving

Eighteen configurations trained to the end would be eighteen trainings. But most configurations show early that they are no good: a learning rate that diverges does so in the first minutes.

Successive halving [5] uses that: train every configuration a little, keep the best third, train those three times longer, keep the best third again. Hyperband[6] runs several such brackets, from many short trials to a few long ones, because nobody knows in advance how early the good ones show; we run one.

A trial is one configuration with its own model, optimizer and W&B run, able to train for a given number of half-epochs and to pick up where it stopped:

class Trial:
    def __init__(self, number, config, run=None):
        self.number, self.config = number, config
        self.model = new_model(dropout=config["dropout"], seed=SEED + number)
        self.optimizer = training.adam(self.model)
        self.steps, self.epochs, self.history = 0, 0.0, []
        if run is None:  # every trial is a W&B run of its own, all of them open at once
            run = wandb.init(project=PROJECT, mode=WANDB_MODE,
                             group="lesson 6: successive halving", name=f"trial {number}",
                             config=config, reinit="create_new")
        self.run = run

    def schedule(self, step):
        warmup, peak = self.config["warmup"], self.config["peak_lr"]
        return peak * min(step / warmup, math.sqrt(warmup / step))

    def train(self, half_epochs):
        own_batches = batches[self.config["batch_tokens"]]
        n_steps = max(1, int(len(own_batches) / 2 * half_epochs))
        smoothing = self.config["label_smoothing"]
        training.train_steps(self.model, self.optimizer, own_batches, self.schedule,
                             n_steps, pad_id=PAD, first_step=self.steps + 1,
                             label_smoothing=smoothing, device=device)
        self.steps += n_steps
        self.epochs += half_epochs / 2
        loss = training.validation_loss(self.model, valid_batches, pad_id=PAD,
                                        device=device)
        self.history.append({"epochs": self.epochs, "validation loss": loss})
        self.run.log({"epochs": self.epochs, "validation loss": loss})
        return loss

And the search: every rung trains the survivors up to its budget, ranks them by validation loss and keeps the best third. This is the long cell of the lesson.

RUNGS = [1, 3, 9]  # cumulative budget of each rung, in half-epochs
KEEP = 3  # keep the best 1 / KEEP

trials = [Trial(number, config) for number, config in enumerate(configs)]
survivors = list(trials)
done = 0
start = time.perf_counter()
for rung, budget in enumerate(RUNGS):
    for trial in survivors:
        trial.train(budget - done)
    done = budget
    survivors.sort(key=lambda trial: trial.history[-1]["validation loss"])
    minutes = (time.perf_counter() - start) / 60
    print("rung", rung, "|", len(survivors), "trials at", budget / 2, "epochs |",
          round(minutes), "min")
    if rung < len(RUNGS) - 1:
        survivors = survivors[: max(1, len(survivors) // KEEP)]
winner = survivors[0]

Watch the order change between rungs. After half an epoch the leaders are the fast starters: high learning rates, short warm-ups, small batches, which get more steps into the same half epoch. The configuration that wins at the end needn’t be among them.

Trap

Decisions made on short runs favour whatever pays off early; the problem has a name, short-horizon bias[7], and it is the price of stopping early. Keeping a third at every rung rather than a tenth is our insurance against it.

7. The winner, trained to the end

The winner of section 5 has trained for four and a half epochs. Successive halving’s last step is to let the survivor finish: one epoch at a time, to the twenty epochs of lessons 3 and 5, keeping the best weights.

The gain is about half of what lesson 5’s four changes to the architecture bought over the 2017 design trained the same way. The validation loss moved much further than COMET did: a lower loss doesn’t turn one for one into better translations.

A search doesn’t replace a better model. It replaces a habit: lesson 5 trained a new architecture with the numbers of 2017, and they turned out to be close to right, not right.

One number escaped the search: twenty epochs, lesson 3’s budget, inherited and never searched over. The last three epochs printed above show the loss had stopped falling, so this time twenty was enough.

8. The same search as a W&B Sweep

Our search ran in one notebook, one trial after another. W&B Sweeps moves the controller to a server: it holds the search space and the method, hands configurations out to agents, and stops runs that fall behind.

Any number of agents on any machines can work on one sweep, and that is how the same search goes from a free T4 to a cluster.

It can also search less blindly than at random. With method: bayes the controller fits a model of the loss as a function of the settings, a Gaussian process[8], and picks the next configuration where it expects the most improvement: where the predicted loss is low, or where the model is still unsure.

The search space in W&B’s terms is a dictionary, the same space as section 4:

SWEEP = {
    "method": "bayes",
    "metric": {"name": "validation loss", "goal": "minimize"},
    "parameters": {
        "peak_lr": {"distribution": "log_uniform_values", "min": 2e-4, "max": 1e-2},
        "warmup": {"distribution": "q_log_uniform_values", "min": 200, "max": 4_000,
                   "q": 1},
        "dropout": {"distribution": "uniform", "min": 0.0, "max": 0.3},
        "label_smoothing": {"distribution": "uniform", "min": 0.0, "max": 0.2},
        "batch_tokens": {"values": BATCH_TOKENS},
    },
    "early_terminate": {"type": "hyperband", "min_iter": 1, "eta": 3},
}

Each run of the sweep is a function the agent calls: it reads its configuration from W&B, trains for up to three half-epochs, and logs the validation loss after each, which is what the early stopping watches.

def sweep_run():
    with wandb.init() as run:  # the agent filled run.config with the controller's choice
        trial = Trial(0, dict(run.config), run=run)
        try:
            for _ in range(3):
                trial.train(1)
        except Exception as error:
            if type(error) is not Exception:  # a real error, not the controller's stop
                raise
            # early stopping: the agent stops a run by raising a bare Exception inside it
            print(f"{run.name}: stopped by the controller after {trial.epochs} epochs")


SWEEP_RUNS = 6
if WANDB_MODE == "online":
    sweep_id = wandb.sweep(SWEEP, project=PROJECT)
    wandb.agent(sweep_id, function=sweep_run, count=SWEEP_RUNS)
    swept = wandb.Api().sweep(f"{wandb.Api().default_entity}/{PROJECT}/{sweep_id}")
    rows = []
    for swept_run in swept.runs:
        rows.append({"run": swept_run.name, "state": swept_run.state,
                     "validation loss": swept_run.summary.get("validation loss"),
                     **{k: swept_run.config.get(k) for k in SWEEP["parameters"]}})
    print("the sweep:", swept.url)
    display(table(pd.DataFrame(rows).sort_values("validation loss"), digits=4))
else:
    print("no W&B key: the sweep needs W&B's servers, so this cell does nothing offline")

Six runs give a Gaussian process little to model; Bayesian optimization pays off over dozens of trials, not a handful.

For engineers

Two details from W&B’s own source are worth knowing. The model is a Gaussian process with a Matérn kernel, choosing by expected improvement. And the “hyperband” of the configuration is a simpler rule than the paper’s: when a run reports its metric for the \(n\)-th time, it is stopped if it is worse than the best third of the runs that got that far.

The lines above the table are that rule at work: the controller stopped the runs it judged hopeless after a report or two, and their GPU time went to the next configuration.

One thing here is not reproducible. W&B’s controller has no seed, so the sweep proposes other configurations every time the notebook runs, and its table changes with them; everything else in the lesson comes out the same.

What this section shows is the machinery: a search space in one dictionary, and as many GPUs as you can find.
